# 공개 콘텐츠 목록 부하 테스트 Before/After 측정 기록

## 메타데이터

- 상태: 측정 대기
- 개선 유형: 성능, 안정성
- 범위: `GET /api/v1/contents` 공개 콘텐츠 목록 조회
- 기준 시각·시간대: 2026-09-07 KST
- Before revision: `9826bfd3f8d38a11826267875209efb3c93efa1b` 기반 작업 트리
- After revision: 미정
- 관련 결정: [ADR-0133](../adr/0133-isolate-public-content-list-load-test.md)
- 측정 환경: MySQL 8.0.42, Redis 7.2.16, Amazon Corretto Java 21, 호스트 k6 2.1.0

## 개선 계약

### 목표

공개 콘텐츠 200개를 반환하는 목록 API의 25·50·100 RPS 구간을 서로 독립적으로 측정하고, k6와 JVM·DB·Redis·Docker
증거 중 최소 두 종류가 일치하는 병목만 개선 대상으로 확정한다. 이 기록은 실제 Before와 After 측정이 모두 끝나기 전에는
성능 개선이나 운영 처리 용량을 주장하지 않는다.

### 불변 조건

- 공개 HTTP 계약, 기존 k6 시나리오, 운영 Compose와 제품 코드는 변경하지 않는다.
- 공개 지역 1개, 콘텐츠·대표 이미지 각 200개, 회차 600개를 사용한다.
- 네 요청 변형은 각각 25%이고 필터 결과는 200·200·100·100건이어야 한다.
- Before와 After의 이미지, 자원 제한, fixture, RPS, VU 할당, 워밍업·측정 시간과 반복 횟수를 같게 유지한다.
- HTTP·계약 오류와 `dropped_iterations`가 하나라도 있으면 해당 실행을 비교 표본에서 제외한다.

### 합격 기준

| 지표 | 합격 기준 | 요약 방법 |
| --- | --- | --- |
| 실행 안정성 | 전·후반 4분 P95 차이 10% 이하, 처리량 차이 5% 이하 | 각 실행을 먼저 개별 판정 |
| 개선 효과 | 병목 RPS의 After P95 중앙값이 Before보다 최소 10% 감소하고 측정 잡음을 초과 | RPS별 유효 실행 3회의 중앙값 |
| 회귀 | 오류·누락 0, 처리량·DB·Redis·JVM 지표 악화 없음 | 원시 지표와 중앙값 함께 확인 |
| 병목 근거 | k6, MySQL, Redis, JVM·Docker 중 최소 두 종류가 같은 원인을 지지 | 실행별 증거 링크 기록 |

## 재현 조건

- 기본 실행: `./performance/k6/run-public-content-list-load.ps1 -Phase Before`
- After 실행: 동일 코드와 환경에서 `-Phase After`만 변경한다.
- 기본 부하: 25·50·100 RPS, RPS별 3회, 실행마다 5분 JVM 워밍업 후 `public-content:*` 200개 재적재와 8분 측정
- 자원 상한: API 2 CPU/1,024 MiB, MySQL 1.5 CPU/1,536 MiB, Redis 0.5 CPU/256 MiB
- 결과 위치: `performance/k6/results/public-content-list-load/<UTC 시각>-<phase>/`이며 원시 결과는 Git에 커밋하지 않는다.

### 수집·판정 경로 단축 검증

기본 측정 결과로 사용하지 않는 1 RPS·5초 워밍업·30초 측정을 한 번 실행했다. 공개 콘텐츠 캐시 200개가 한 번에
재적재되고 최소 TTL이 595,919ms임을 확인했다. k6 요청 30회에서 HTTP·계약 오류와 drop은 0이었고,
Actuator 35개 표본, Docker 15개 표본, MySQL `performance_schema` 전·후 snapshot, Redis `INFO` 전·후 snapshot을
모두 저장했다.

단축 실행은 전반 P95 414.53ms, 후반 P95 218.11ms로 차이가 47.38%여서 10% 안정성 기준을 통과하지 못했다.
전·후반 처리량은 각각 1.0 RPS로 차이 0%였다. 이는 30초 진단 실행이 비교 표본으로 부적합하며 안정성 게이트가
실제로 실패를 차단한다는 검증 결과일 뿐, 제품 성능 판정에 사용하지 않는다.

### 저장소 회귀

`./gradlew.bat fastTest`는 2,350건 중 2,349건이 통과하고 기존
`SessionRevisionRejectionAuditAtomicityTest` 1건이 실패했다. 단독 재실행에서도 같은 실패가 재현됐다. 테스트의 고정
Clock은 2026-08-05이지만 네이티브 쿼리는 현재 DB 시각을 사용하고 고정 회차가 2026-08-27이어서, 실행일
2026-09-07에는 감사 저장 실패 경로 전에 과거 회차 검증에서 `BusinessException`이 발생한다. 이번 변경은 제품 Java와
테스트 코드를 수정하지 않으며 이 기존 시간 의존 실패는 Before/After 성능 표본과 분리한다.

## 변경 내용

병목 분석과 개선은 아직 수행하지 않았다. 먼저 Before 본 측정과 둘 이상의 지표 근거로 병목을 확정한 뒤, 공개 계약을
유지하는 최소 변경만 별도 작업으로 적용한다. 목록 전체 반환 비용이 원인이면 목록 계약을 바꾸지 않고 공개 콘텐츠 상세
API 측정으로 전환한다.

## 비교와 판정

Before·After 본 측정값이 없으므로 개선 판정은 보류한다. 최소 10% 감소 조건이나 병목을 충족하지 않은 결과를 개선으로
기록하지 않는다.

## 한계와 잔여 위험

- 한 조건의 기본 실행 시간은 최소 117분이며 호스트 열 상태와 다른 프로세스의 영향을 받을 수 있다.
- fake 이미지 저장소를 사용하므로 실제 S3 네트워크 비용은 포함하지 않는다.
- `VuMultiplier=2`가 부족하면 `dropped_iterations` 기준이 실행을 실패시키며, Before와 After 모두 같은 값을 사용해야 한다.
- 기존 시간 의존 테스트 실패는 별도 수정 범위이며 현재 성능 테스트 구현에서 우회하지 않았다.
