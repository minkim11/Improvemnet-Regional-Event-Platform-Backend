# ADR-0133: 공개 콘텐츠 목록 부하 테스트를 격리된 로컬 환경에서 독립 RPS로 실행한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-09-07
- 결정일: 2026-09-07
- 관련 요구사항: [PRD 성능·가용성](../local-stamp-platform-prd.md#114-성능가용성), [P0 `FR-02`](../p0/content-catalog.md#fr-02-지역-선택과-콘텐츠-탐색), [공개 콘텐츠 목록 API](../api/p0/content/list-public-contents.md), [ADR-0031](0031-use-version-validated-cache-aside-for-public-content.md)

- 관련 이슈: 없음
- 대체 대상: 없음

## 맥락

공개 콘텐츠 목록은 콘텐츠별 정적 표시 정보만 Redis에 저장하고, 공개 상태·버전·회차·예약 가능 여부는 매 요청마다
MySQL에서 확인한다. 기존 k6 시나리오는 고정 VU로 여러 공개 API를 함께 호출하므로 목록 단일 경로의 유입률과
병목 지점을 분리해 측정할 수 없다. 실제 트래픽과 제품 SLO가 아직 없으므로 운영 용량을 주장하지 않고, 같은 로컬
환경과 데이터에서 요청 유입을 단계적으로 높여 캐시 적중 뒤 남는 병목을 찾을 재현 가능한 측정 계약이 필요하다.

공개 목록은 페이지네이션을 제공하지 않으므로 결과 수가 응답 조립 비용에 직접 영향을 준다. 다만 이번 측정은 공개
계약을 변경하기 위한 작업이 아니라 기존 계약 안에서 구현 병목을 찾는 작업이다.

## 결정 동인과 불변 조건

- 운영·공유 개발 환경과 분리된 로컬 Docker 환경에서만 실행한다.
- 기존 공개 API 계약, 캐시 키·TTL, MySQL 최종 정합성 원칙과 기존 k6 시나리오를 변경하지 않는다.
- warm-cache 측정에 Redis TTL 만료나 fixture 생성 비용을 섞지 않는다.
- RPS별 응답 시간·처리량과 애플리케이션·MySQL·Redis 지표를 같은 시간축으로 기록한다.
- Before와 After는 같은 이미지, 자원 제한, fixture, 부하, 반복 횟수와 VU 할당을 사용한다.
- 실제 사용자 수, 운영 SLO 또는 AWS 배포 용량으로 결과를 일반화하지 않는다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 전용 Compose에서 RPS별 `constant-arrival-rate`를 독립 실행 | 단계별 지표와 Before/After를 직접 비교할 수 있고 자원·버전을 고정할 수 있다. | 실행 시간이 길고 로컬 장비에만 유효하다. | 낮음. 전용 파일을 제거하면 된다. | 추천안이며 사용자가 채택했다. |
| 2 | 한 실행에서 `ramping-arrival-rate`로 25→50→100 RPS를 올림 | 실행 횟수와 총 시간이 적다. | 단계별 percentile 분리와 이전 단계의 JVM·DB 영향 제거가 어렵다. | 낮음 | 병목 근거와 Before/After 비교가 불명확하다. |
| 3 | 기존 고정 VU 공개 API 시나리오를 확장 | 새 파일이 적다. | 목록 외 API와 closed-model 부하가 섞이고 기존 회귀 기준이 바뀐다. | 중간 | 기존 시나리오 보존 조건에 맞지 않는다. |

## 결정

MySQL 8.0.42, Redis 7.2.16, Java 21 API를 실행하는 성능 전용 Compose를 추가하고 API·MySQL·Redis의 자원
상한을 고정한다. 호스트의 k6는 전용 네트워크의 API 공개 포트만 호출한다. fixture는 공개 지역 하나에 콘텐츠
200개, 대표 이미지 200개, 콘텐츠별 회차 3개를 생성하며 예약 가능 콘텐츠와 불가능 콘텐츠를 각각 100개로
고정한다.

목록 요청 한 건을 iteration 한 건으로 두고 25, 50, 100 RPS를 `constant-arrival-rate`로 각각 실행한다. 각
RPS는 5분 워밍업 뒤 공개 카탈로그 prefix만 삭제·재적재하고 8분 동안 측정하며 세 번 반복한다. 8분은 기본 캐시
TTL 10분 안에서 만료 재적재를 피하면서 최저 25 RPS에서도 약 12,000개 표본을 확보하는 기간이다. 100 RPS까지
병목 신호가 없을 때만 같은 조건으로 200 RPS를 추가한다.

필터는 지역만, 콘텐츠 유형 포함, 예약 가능 `true`, 예약 가능 `false` 네 종류를 같은 비율로 반복한다. k6 결과와
Docker, Actuator, MySQL `performance_schema`, Redis `INFO`를 함께 보관한다. HTTP·계약 오류와
`dropped_iterations`는 허용하지 않는다. 응답 시간 수치는 SLO가 아니라 병목 탐색과 동일 조건 비교에만 사용한다.

목록 전체 반환과 콘텐츠별 응답 조립이 주된 병목으로 확인되면 페이지네이션이나 응답 캐시를 이번 작업에 추가하지
않는다. 목록 개선을 중단하고 같은 버전 검증형 캐시를 사용하는 단건 공개 콘텐츠 상세 API를 다음 측정 대상으로
선택한다.

## 결과와 트레이드오프

### 기대 효과

- 부하 단계별 처리량과 percentile을 다른 API나 이전 단계의 집계와 섞지 않는다.
- 캐시 적중 상태에서 MySQL, Redis, JVM 중 병목 근거를 같은 실행에 연결할 수 있다.
- 기존 회귀 시나리오와 공개 계약을 보존하면서 측정 도구만 독립적으로 제거하거나 변경할 수 있다.

### 수용한 단점과 위험

- Before 또는 After 한쪽의 전체 3회 측정에 최소 117분이 필요하다.
- fake 이미지 저장소를 사용하므로 실제 S3 presigner와 네트워크 지연은 측정하지 않는다.
- 200개 콘텐츠는 재현용 진단 규모이며 실제 지역별 콘텐츠 분포를 대표하지 않는다.
- 호스트 열 상태와 Docker Desktop 자원 경쟁은 완전히 제거할 수 없어 실행 안정성 검사가 필요하다.

## 전환과 롤백

ADR 확정 뒤 전용 Compose, fixture, k6 시나리오와 러너를 추가한다. 운영 Compose, 제품 설정, 공개 API와 기존
k6 파일은 변경하지 않는다. 전용 환경의 health, fixture 건수, smoke 검증이 실패하면 부하 측정을 시작하지 않는다.

문제가 있으면 전용 Compose와 부하 테스트 파일을 제거해 되돌린다. 데이터 이관이나 호환 계층은 없다. 이후 실제
트래픽이나 SLO가 확정되면 이번 진단 RPS를 운영 용량으로 재사용하지 않고 새 부하 모델을 별도로 결정한다.

## 검증 방법

- `docker compose config`로 이미지, 자원 상한, 네트워크와 loopback 포트를 확인한다.
- fixture 적용 뒤 콘텐츠 200개, 이미지 200개, 회차 600개와 필터별 200·200·100·100건을 검증한다.
- `k6 inspect`와 1 RPS smoke에서 요청 계약과 결과 파일 생성을 확인한다.
- 측정 실행마다 목표 처리량, 오류율, `dropped_iterations`, 전·후반 P95 안정성, 캐시 키 수와 TTL을 검증한다.
- MySQL digest·실행 계획, Redis hit/miss·명령 통계, JVM·Hikari·컨테이너 자원 중 둘 이상의 증거로 병목을 확정한다.
- Before와 After 각각 세 번의 개별값과 중앙값을 같은 개선 로그에 기록한다.

## 대체 조건

- 실제 접근 로그와 제품 SLO가 확정되어 평균·피크 트래픽 기반 부하 모델이 필요해진다.
- 콘텐츠 규모 200개 또는 단일 API 인스턴스가 더 이상 파일럿 환경을 설명하지 못한다.
- 분산 k6, Prometheus·Grafana 또는 실제 S3 연동 없이는 병목을 판별할 수 없는 증거가 나온다.
- 기본 캐시 TTL이나 공개 콘텐츠 목록 계약이 별도 결정으로 변경된다.
