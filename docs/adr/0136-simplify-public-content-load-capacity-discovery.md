# ADR-0136: 공개 콘텐츠 부하테스트를 단계형 처리 한계 탐색으로 단순화한다

- 결정일: 2026-09-14
- 관련 요구사항: [PRD 성능·가용성](../local-stamp-platform-prd.md#114-성능가용성), [공개 콘텐츠 목록 API](../api/p0/content/list-public-contents.md), [ADR-0133](0133-isolate-public-content-list-load-test.md)

## 맥락

기존 측정은 RPS별 3회 반복과 `dropped_iterations == 0`을 엄격히 적용해 하나의 측정이 실패하면 이후 RPS까지
수집하지 못했다. 최근 50 RPS 측정에서는 HTTP·계약 오류가 없었지만, 200 VU가 모두 사용되어 목표 50 RPS 중
47.22 RPS만 시작했고 1,326개 iteration이 누락됐다. 이 결과에는 서버 지연과 부하 생성기의 VU 상한이 함께
반영되어 비전공자가 서버의 처리 한계와 k6의 요청 누락을 구분하기 어려웠다.

현재 목적은 운영 SLO 인증이나 정확한 최대 처리량 산정이 아니라, 25·50·100 RPS 중 처리량이 꺾이는 구간과 그때
포화되는 자원 후보를 짧고 반복 가능하게 찾는 것이다. 정확한 한계가 필요할 때만 확인된 구간을 더 작은 RPS 간격으로
다시 측정할 수 있다.

## 결정 동인과 불변 조건

- 공개 HTTP 계약, fixture, 전용 Compose 자원 제한과 8분 warm-cache 측정 조건은 유지한다.
- HTTP·계약 오류와 목표 처리량 미달을 서로 구분한다.
- 한 단계의 실패가 다음 RPS의 증거 수집을 막지 않는다.
- 부하 생성기의 VU 부족이 서버 처리 한계보다 먼저 발생하지 않도록 최근 P95보다 큰 동시성 여유를 둔다.
- 캐시 개선 효과는 추정값이 아니라 같은 단계형 Before/After에서 실제 통과한 최고 RPS로 표현한다.

## 검토한 선택지

| 순서 | 선택지 | 장점 | 단점·실패 위험 | 되돌림 비용 | 현재 단계 적합성 |
| --- | --- | --- | --- | --- | --- |
| 1 | 25·50·100 RPS 단계형 간단 탐색 | 정상·한계·과부하 구간을 쉽게 설명하고, 실패 뒤에도 모든 단계 증거를 남길 수 있다. | 정확한 한계는 두 RPS 사이 범위로만 알 수 있다. | 낮음 | 추천안이며 사용자가 채택했다. |
| 2 | 작은 간격의 자동 최대 RPS 탐색 | 더 정확한 최대 처리량을 찾을 수 있다. | 실행 시간과 제어 코드가 늘고 로컬 변동을 최대값으로 오해하기 쉽다. | 중간 | 현재 병목 후보 탐색에는 과도하다. |
| 3 | 고정 VU·고정 시간 측정 | 실행 모델이 익숙하고 단순하다. | 응답이 느려질수록 유입률도 낮아져 RPS별 캐시 전후 용량을 직접 비교할 수 없다. | 낮음 | RPS 처리 한계 탐색에 부적합하다. |

## 결정

기본 부하는 25·50·100 RPS를 각각 한 번 측정한다. 각 단계는 기존 25 RPS 5분 워밍업, 30초 무부하 대기,
캐시 재적재, 8분 본 측정 순서를 유지한다. 기본 VU는 목표 RPS의 10배로 미리 할당한다. 이는 최근 50 RPS의
P95 5.20초보다 큰 10초의 동시성 예산으로, 해당 예산까지 소진되면 그 사실도 과부하 증거로 기록한다.

각 단계는 HTTP·계약 오류가 없고 실제 HTTP 요청률이 목표의 95% 이상이면 `정상`이다. 이 조건을 처음 만족하지
못한 단계는 `한계`, 그보다 높은 실패 단계는 `과부하`로 표시한다. `dropped_iterations`는 별도의 즉시 실패 조건이
아니라 실제 요청률 미달 원인을 설명하는 지표로 사용한다. 이전 정상 단계보다 P95가 두 배 이상 증가하면 처리 실패와
별개로 `응답시간 급증` 경고를 남긴다. 절대 P95 합격값은 제품 SLO가 없으므로 만들지 않는다.

k6의 threshold 실패 종료 코드 99는 해당 단계 결과에 기록하고 다음 반복과 RPS를 계속한다. 스크립트 오류나 실행
환경 오류 등 다른 종료 코드는 전체 실행을 중단한다. 루트 결과 디렉터리에 단계별 목표·실제 RPS, P95, drop,
HTTP·계약 오류, 판정과 처리 한계 범위를 모은 단일 Markdown 요약을 생성한다.

캐시 개선은 같은 조건의 After 실행에서 `정상`으로 통과한 최고 RPS가 상승했을 때만 처리 구간 개선으로 설명한다.
예를 들어 Before가 25 RPS 정상·50 RPS 한계이고 After가 50 RPS 정상·100 RPS 한계이면, 검증된 처리 구간이
25 RPS에서 50 RPS로 상승했으며 정확한 After 한계는 50~100 RPS 사이라고 기록한다.

## 결과와 트레이드오프

### 기대 효과

- 한 파일만 읽어도 정상 구간, 최초 한계와 과부하 단계를 구분할 수 있다.
- VU 부족에 의한 요청 누락과 서버의 HTTP·계약 오류를 혼동하지 않는다.
- 하나의 실패 때문에 더 높은 RPS의 병목 증거가 사라지지 않는다.
- 캐시가 해결할 수 있는 RPS를 사전 추정하지 않고 Before/After 실측 범위로 설명한다.

### 수용한 단점과 위험

- 기본 3개 단계만으로는 정확한 최대 RPS를 알 수 없다.
- 단일 실행은 성능 개선을 확정할 통계적 반복 근거가 아니며 병목 후보 탐색에만 사용한다.
- 목표 RPS의 10배 VU를 넘는 지연에서는 다시 부하 생성기 상한이 결과에 포함된다.
- 로컬 Docker 결과를 운영 용량이나 SLO로 일반화할 수 없다.

## 전환과 롤백

데이터 이관이나 공개 계약 호환 계층은 필요 없다. 러너의 기본 반복과 VU 배수, k6 처리량 threshold, 단계 실패
처리와 최종 요약만 변경한다. 기존 원시 결과 형식과 파일은 유지한다. 탐색 결과가 지나치게 거칠면 `-Rates`로
확인된 한계 구간만 더 잘게 지정한다. 새 판정이 목적에 맞지 않으면 이전 반복 횟수와 drop 0 조건으로 되돌릴 수 있다.

## 검증 방법

- `k6 inspect`에서 목표 요청률의 95% threshold와 충분한 VU가 적용되는지 확인한다.
- 합성 k6 summary로 정상, 최초 한계, 이후 과부하와 P95 급증 판정을 검증한다.
- threshold 종료 코드 99 뒤 다음 RPS 디렉터리와 최종 요약이 생성되는지 확인한다.
- 실제 탐색에서는 각 단계의 목표·실제 RPS, HTTP·계약 오류, drop, P95와 수집된 JVM·Docker·MySQL·Redis 증거를 함께 확인한다.
- Before/After는 같은 RPS, Compose, fixture, 워밍업과 측정 시간을 사용한다.

## 대체 조건

- 운영 SLO나 실제 트래픽이 확정되어 절대 응답시간과 오류 예산으로 용량을 승인해야 한다.
- 단계 간격이 넓어 개선 전후의 통과 최고 RPS가 같게 반복된다.
- 10초 동시성 예산에서도 k6 호스트 CPU·메모리가 먼저 포화된다는 증거가 나온다.
- 단일 실행의 로컬 변동 때문에 병목 후보가 반복해서 달라진다.
