# ADR-0135: 공개 콘텐츠 부하 측정에서 워밍업 부하를 분리한다

- 상태: 채택됨
- 기록 유형: 신규
- 기록일: 2026-09-14
- 결정일: 2026-09-14
- 관련 요구사항: [공개 콘텐츠 목록 API](../api/p0/content/list-public-contents.md), [ADR-0133](0133-isolate-public-content-list-load-test.md), [ADR-0134](0134-warn-on-public-content-load-time-variance.md)
- 관련 단계: 단계 1. MVP 구현·검증
- 관련 이슈: 없음
- 대체 대상: [ADR-0133](0133-isolate-public-content-list-load-test.md)의 목표 RPS별 워밍업 부하와 본 측정 전환 순서

## 맥락

ADR-0133은 각 목표 RPS와 같은 유입률로 5분 워밍업한 직후 캐시를 재적재하고 본 측정을 시작하도록 정했다.
실제 50 RPS 워밍업 두 번은 각각 P95 3,227.69ms와 6,499.51ms, `dropped_iterations` 1,602개와
1,828개를 기록했다. 뒤이은 본 측정은 전반 4분 P95가 2,220.28ms와 4,274.91ms였지만 후반 4분에는
277.88ms와 231.73ms로 회복했다. 워밍업 자체가 포화 부하가 되어 남긴 적체가 본 측정 초반에 섞였으므로,
목표 RPS의 지속 처리 능력과 워밍업 잔여 부하를 비전공자도 구분해 설명하기 어렵다.

25 RPS는 HTTP·계약 오류와 `dropped_iterations` 없이 처리됐고 5분 동안 약 7,500회 같은 목록 경로와 네 요청
변형을 실행할 수 있다. 따라서 JVM 코드 경로를 준비하는 워밍업 부하로 사용하되, 본 측정 전에 무부하 구간을 두어
진행 중인 요청과 연결 대기를 정리할 필요가 있다.

## 결정 동인과 불변 조건

- 워밍업은 JVM과 동일 요청 경로를 준비하되 API를 포화시키지 않아야 한다.
- 본 측정에는 워밍업에서 시작한 요청과 연결 대기를 섞지 않는다.
- 5분 워밍업, 8분 측정, 캐시 TTL 10분과 목표 25·50·100 RPS는 유지한다.
- 캐시 prefix 재적재는 무부하 대기 뒤에 수행해 본 측정의 TTL 여유를 유지한다.
- Before와 After는 같은 워밍업 RPS와 무부하 대기 시간을 사용한다.
- 공개 HTTP 계약, fixture, Compose 자원 제한과 기존 k6 시나리오는 변경하지 않는다.

## 결정

모든 목표 RPS 실행은 공개 콘텐츠 목록을 25 RPS `constant-arrival-rate`로 5분 워밍업한다. 워밍업 k6가
종료된 뒤 30초 동안 새 부하를 보내지 않고 기다린다. 그 다음 공개 카탈로그 cache prefix를 삭제·재적재하고
MySQL·Redis 사전 snapshot을 저장한 뒤 목표 RPS의 8분 본 측정을 시작한다.

워밍업의 VU 수는 워밍업 RPS 25에 기존 `VuMultiplier`를 적용하고, 본 측정의 VU 수는 목표 RPS에 같은 배수를
적용한다. 결과의 `environment.json`에는 워밍업 RPS와 무부하 대기 시간을 저장해 Before와 After 조건 차이를
확인할 수 있게 한다. 워밍업의 `dropped_iterations`는 진단 정보로 남기되 본 측정을 중단시키지 않고, 본 측정의
오류·계약·drop 실패 조건은 유지한다.

## 결과와 트레이드오프

### 기대 효과

- 워밍업 적체가 본 측정 초반 P95와 VU 사용량에 섞이는 현상을 줄인다.
- 25·50·100 RPS 결과를 각각 정상, 한계, 초과 구간으로 설명하기 쉬워진다.
- 캐시 TTL, 본 측정 시간과 기존 결과 파일 형식을 유지한다.

### 수용한 단점과 위험

- 30초는 고정 대기이므로 비정상적으로 오래 실행되는 요청을 상태 기반으로 증명해 제거하지는 않는다.
- 워밍업보다 높은 목표 RPS에서 필요한 동시 객체 할당과 스레드 경합은 본 측정 중 처음 발생할 수 있다.
- 이 변경 전 결과는 워밍업 조건이 달라 변경 후 결과와 정식 반복 표본으로 합치지 않는다.

## 전환과 롤백

부하테스트 실행기의 워밍업 RPS를 25로 고정하고 워밍업과 캐시 재적재 사이에 30초 대기를 추가한다. 결과 JSON에
두 조건을 추가하지만 기존 필드는 유지하므로 데이터 이관이나 호환 계층은 필요하지 않다. 변경 뒤 25 RPS에서도
불필요한 대기만 늘거나 본 측정 초반 적체가 반복되면 대기를 제거하고 ADR-0133의 전환 순서로 되돌릴 수 있다.

## 검증 방법

- PowerShell 구문 검사로 실행기 변경이 Windows PowerShell 5.1에서 해석되는지 확인한다.
- 정적 검사로 워밍업 `PERF_RATE`와 VU가 25 RPS 기준이고 본 측정은 목표 RPS 기준인지 확인한다.
- `environment.json`에 `warmupRate=25`, `warmupCooldownSeconds=30`이 저장되는지 확인한다.
- 50 RPS 1회에서 워밍업 종료와 본 측정 시작 사이 30초 이상이 확보되고 캐시 재적재가 그 사이 이후에 실행되는지 확인한다.
- 변경 후 50 RPS의 전·후반 P95, 처리량, drop과 API CPU를 이전 결과와 분리해 기록한다.

## 대체 조건

- 25 RPS 워밍업에서도 HTTP 오류나 지속적인 적체가 발생한다.
- 30초 뒤에도 워밍업 요청이나 Hikari pending이 남는 증거가 반복된다.
- 운영 SLO 검증 단계에서 목표 동시성에 맞춘 단계형 워밍업이나 상태 기반 안정화가 필요해진다.
